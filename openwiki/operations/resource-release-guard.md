# Windows resource release guard

The collector measures idle CPU over a clean ten-second interval, then collects up to four timestamped job snapshots plus the final snapshot used for comparison. CIM data is captured and indexed by PID before the stable job-accounting bracket; process identity is checked by PID and creation time. Every owned process must have a matching CIM command line, executable path, parent ID and creation time; the creation time must match the process start time. Job accounting must remain stable throughout each capture. Missing or mismatched evidence retries at most ten times, then fails closed. These short samples help identify changes between instants; they do not prove sustained growth or its absence. Full command lines and paths are retained in the measurement artifact.

The release waits for a Windows resource comparison. Pull requests run the same guard. It downloads the fixed baseline in `limits.json` once per job and verifies its signed checksum manifest, builds the synthetic SSH launcher, then measures the baseline and candidate executables sequentially on the same host. The app executable is real; SSH and tmux are synthetic Python-backed fixtures, not network servers. The fixture seeds thirty saved chat sessions with forty records each; it does not generate the separate large-history fixture.

Each synthetic launcher starts Python suspended, assigns it to a private kill-on-close job, then resumes it. The job nests inside the driver's VerifyJob. Closing or killing the launcher stops its Python descendants; setup failures stop the launch. Both resource workflows exercise the compiled fixture's child and grandchild lifetime and normal exit code on hosted Windows.

Before IGSH-1967 the usage collector ran as a second hidden copy of the app and derived its repository root by taking three parents of its executable path. Previously the baseline at `baseline-bin/multiprompt-x64.exe` missed the checked-in example config, while the candidate at `zig-out/bin/multiprompt.exe` found it. The baseline collector exited and the candidate collector remained running, making the comparison asymmetric.

Each measurement now stages its supplied executable and its own required `zigshell-bridge.exe` under a fresh private profile at `app/bin/`. The public example config and Kimi helper are staged at `tools/usage-telemetry/` within that profile; no local config or credentials are copied. Evidence records input and staged paths and hashes. The comparator requires matching telemetry config and helper hashes across measurements. All processes remain in the existing comparison; the usage collector is no longer a process of its own, and future process growth still fails.

For each executable, the driver starts a fresh profile in a kill-on-close Windows job, waits for its owned main window and thirty saved Chat View tabs, and switches through all thirty distinct chats until each reports nonempty painted content. It settles, samples job CPU across ten seconds, and enumerates the job's processes and working sets. A process snapshot must agree with the job's active count. Missing evidence, dropped tabs, an exited app, failed cleanup, or a missing synthetic SSH process fails the gate. Raw process lists, job accounting, logs, hashes and saved tabs are artifacts.

Candidate process count, synthetic SSH process count, SSH reader process count, job-owned console count and directly attributed external console count cannot exceed baseline. External console evidence must identify unique console PIDs with owned direct parents. Candidate working set may exceed baseline by at most 16 MiB to absorb host noise; this tolerance is provisional and must be checked against repeated hosted runs. Idle CPU is reported, not gated. The SSH reader count identifies owned fixture SSH processes with legacy `--serve` or `--watch` arguments or the shared Python bootstrap command. It is a synthetic transport-process proxy, not a TCP connection or per-chat reader count. CIM reports console processes whose direct parent is in the job; Windows can host consoles elsewhere, so this is not complete console attribution. Working set covers job members, not proven external console hosts. Targets are aspirational, not fabricated measurements.

After resource snapshots, the driver waits up to 15 seconds for composer focus before each switch, acquiring it only when needed. Each loaded tab receives a real keyboard character and Enter. Typing measures from input injection until the owned native composer reports the character; it is not a pixel-paint measurement. Send timing uses the app's enqueue-to-transcript-paint debug instrumentation. Raw samples, session IDs, methods and collection errors are saved with each measurement. Both metrics require all thirty distinct sessions; incomplete evidence is unmeasured. Typing above 50 ms and send paint above 300 ms warn only. On trusted releases, each measured warning searches Fleet CI for its own open matching ticket before creating one, using the existing release agent secret. Pull requests never file tickets. These synthetic SSH sessions do not prove hosted agent delivery.

Synthetic SSH does not use TCP. Established TCP connections of all job-owned processes are collected separately through Windows CIM. Each row retains local and remote addresses and ports and its owning PID. Enumeration occurs inside the stable job-accounting bracket; collection errors fail the measurement. Empty results are valid. The candidate count cannot exceed baseline; this does not prove real SSH connectivity. External console attribution covers direct parentage only and may miss consoles. Idle CPU is measured over ten seconds and reported, but has no blocking threshold. Hosted Windows runs must verify the new latency collection and ticket behavior before claiming release proof.

## Controlled warning-ticket proof

After this workflow is on `master`, manually dispatch `resource-warning-integration.yml` on `master`. It runs on GitHub-hosted Ubuntu with Node 22. Only the integration step receives `HYPERTASK_AGENT_TOKEN`. The targeted unit tests must pass first; no pull request runs this proof. The job serializes proof runs and uses the dispatched commit and run URL as evidence.

The proof creates synthetic send and typing warnings on Fleet CI (11514), using fixed `HYCI-168 verification` titles and the production search, labels, creation and deduplication paths. These records do not indicate real slowness. For each metric it requires one creation and the same existing ticket on repeat. It moves only tickets identified in this run's successful creation responses to Done, then reads them back. It never deletes tickets.

Download `resource-warning-integration-evidence` and check both metrics, their ticket numbers, and each Done readback. A prior open proof ticket stops the run without closing that ticket. Investigate and resolve leftovers separately before retrying. A canceled job, an ambiguous create response, or an API failure may leave an open record; inspect the board and evidence before another dispatch. A failed or absent artifact is not a successful proof.
