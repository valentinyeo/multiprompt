# Browser routing and isolation

The browser pane stays docked in place and cannot be dragged away or maximized to full screen.

The browser engine uses dedicated `%LOCALAPPDATA%\ZigShell\EdgeUserData` or `ChromeUserData` profiles. Normal browser windows, OS URL launches, and installed web apps do not share that profile. Tabs created inside a protected pane remain in it; navigation provenance is not used to eject them into the user's normal browser.

Each browser-control command requires an exact session and browser window binding. Two sessions never share one browser pane name. When a session name is repeated, it opens in the session in front, and each session keeps the pages in its own pane. App-level `workspace-list` and `session-open` bypass browser routing; see [workspace and tmux tabs](zsb-selftest.md#workspace-and-tmux-tabs). `multiprompt-browser` (`zsb` compatibility alias) uses the current tmux session only when `TMUX` is present. Outside tmux, set `ZSB_SESSION` explicitly. An ambient attached session never authorizes a headless caller.

`navigate` creates a background tab and remembers it as the session's target. It may reuse that tab only if the same session's agent created it, it is still in the bound window, it is inactive, and the user has never selected or navigated it. User takeover permanently revokes reuse authority; worker reload discards it. `navigate --new-tab` always creates a fresh background tab. Navigation never overwrites an active tab or a user tab, and never uses a read/action fallback as reuse authority. The launch beacon is not session content: the first navigate in a bound window loads into the beacon tab in place, a freshly launched pane with no page goes to about:blank, and extension startup removes beacon tabs from windows that also hold other tabs.

Subsequent reads and actions follow the remembered target unless `--tab` selects another tab in the same window. Foreign window/tab IDs fail closed. Commands cannot use a global focused-tab search to repair stale bindings. A stale binding may be re-established through the app's exact-session worker/UI request path. The navigation-commit observer only revokes reuse authority; it cannot eject, move, mute or close tabs.

Physical app actions can transfer keyboard focus. Automated navigation, screenshots, notifications, extension reconnects, and selftests cannot acquire foreground authority. The UI thread must not block waiting for browser commands. Native screenshot delivery uses nonblocking loopback connects/sends with a per-port deadline.

Each chat can keep one pinned page. Desktop session storage keeps that preference. Pin reads that chat's actual browser page. Entering a chat may reopen its pin. Automatic reopening never takes typing focus. Return is an explicit user action. Window transfers carry each pin separately. Transfers may include the last browser address. Confirmation means accepted details and queued saving. Disk writing may still be unfinished.

`MULTIPROMPT_BROWSER_PROFILE` (or `--profile <token>`) sends commands to that profile's own pipe `multiprompt-browser-isolated-<token>` (1 to 32 of `a-z`, `0-9`, `-`, no leading `-`); no token keeps the default pipe, and an unknown or invalid profile fails instead of falling back.

A chat owned by a second OS user runs under that user, so its browser commands cannot use the first user's relay config. The shared runtime installs `zsb`, `multiprompt-browser` and `mp-zsb` in `~/.multiprompt-runtime`, and a hosted chat's `PATH` starts there, so a chat always runs the CLI shipped with its current runtime and never a stale copy in `~/.local/bin`. The delegating host also exports `ZSB_SOCKET=/tmp/mp-browser-<bridge uid>/control.sock`, the first user's owner relay, which any local user may connect to; a connectable relay socket is preferred, then a configured socket, then the relay port. The relay authorises a hosted chat by the `session` record the delegating host writes under `~/.local/state/multiprompt/owner-sessions`, and forwards that session name unchanged so the app routes it to that chat's own pane; terminal chats keep the outer tmux `@owner_user`/`@owner_session` check. An unregistered session, a global app command or a profile switch is refused with `owner_scope_denied`. When no socket answers, a pane port held by anything other than the SSH forwarder (`sshd`) is reported as `port_conflict` with that process id and command instead of `tunnel_down`, so an old `~/.local/share/zigshell/mp_notify_relay.py` that kept 19548 is named rather than blamed on a missing tunnel; an unreachable owner relay reports `relay_unavailable` with the socket path.

The extension and native bridge versions must match. Reload unpacked extension code after changes; `zsb extension-reload` schedules a profile-wide reload and reports acknowledgement, not completed reload. See [zsb-selftest.md](zsb-selftest.md) for installation checks and diagnostics.
