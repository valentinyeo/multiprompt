# Rooms: preview send and legacy safety

## Sub-features

Create a room with two agents. Persist its selection, members and draft. Refuse sending on a legacy peer. On a scoped preview peer, send two questions and receive two explicitly synthetic replies beneath each question without repeats after restarting.

## How to get to it (user POV)

Open Ctrl+K and choose New room. Name it, select two agents, then press Ctrl+Enter. Type a draft and press Enter. Reopen the app with the same profile.

## Driving it with control.ps1

Dispatch `verify.yml` with `feature=rooms`, no release tag, on the isolated Rooms proof branch. The shared build enables `rooms-preview`; release visibility stays unchanged. The Windows driver delegates to `tools/verify-rooms/drive.ps1`. No workflow changes or live account secret are required.

The driver builds the existing account Worker through a local-only Wrangler dry run, then runs it with Miniflare on the disposable hosted Windows machine. As in the account journey, a temporary trusted certificate and hosts entry route the app's normal account origin to that isolated Worker. The fixture generates temporary device credentials, seeds its account layout through the real API, and protects the refresh credential through Windows DPAPI. Interactive sign-in and the production account service are not covered. Cleanup restores the original hosts file, removes both certificate entries, stops the owned service process tree, and deletes the profile and credentials.

Real keyboard input opens the palette and member picker, types Product sync, creates the room, waits for its actual app-owned selection, attempts a legacy send, and checks draft persistence after restart. Creation acceptance must retain the creation view and pending token until the real room model replaces it; the native state regression checks this handoff, stale callbacks, failed creation retry and ordinary edit acceptance. Switching only the remote boundary to scoped synthetic replies then exercises two real native broadcast sends. Independent SQLite reads require exactly two human events and four replies, with each question retaining its own two chosen members and distinct scripted answer text. Canonical event reads require exactly four started and ended turns. Reopening the owned app must load the same selected room without adding messages or turns. No room events or drafts are inserted by the driver. Native typing and key chords run in owned, hidden input helpers with a twenty-second deadline; a blocked SendInput must fail and return control for evidence and cleanup instead of consuming the job timeout.

Before the first broadcast, the synthetic provider boundary marks both agents offline. The actual bridge and canonical transaction must retain two queued deliveries for one human question, with no reply or started/ended turn. The native transcript must paint one question and zero answers. Restarting the owned app while agents remain offline must retain the same two durable message IDs and empty submitted draft, without extra events. Restoring only provider availability and restarting must deliver those original IDs, not create replacements. Separate offline witnesses retain only synthetic room identities, canonical state and events; no profile or credential is exported. This proves the hosted availability stand-in, not a real disconnected host or automatic delivery without reopening.

After the first replies, the synthetic transport holds one catalog or catalog-metadata response for at most twelve seconds. The driver types and submits the second question while that background read is outstanding, then releases only the transport response. An expired hold or immediate admission rejection fails. No app state is written to create the overlap. At most 32 allowlisted rejection classifications may enter evidence; raw debug logs and request content remain excluded. Run 42092334078 on 9dce4226e fails with `busy=catalog` while the hold remains unexpired. The queued-command regression extracts the real completion handoff and checks original identity, exactly-once launch, empty creation identity, stale account/route refusal, launch recovery and interrupted-read rescheduling. A queued command is persisted before waiting; it never cancels transport or repeats keyboard input.

The room composer must be the visible multiline Edit, not the name field cached during asynchronous creation. After send and after restart, the driver also reads actual screen pixels in the owned room's DPI-scaled transcript bounds, excluding header, composer and offline bar. It requires one human and two agent bubbles after the first send, then two human and four agent bubbles after the second question and restart, using the production preview palette. Fourteen DPI-scaled pixels may join interrupted background scans inside a text line; the much larger author/row spacing still separates distinct bubbles. Exact observed counts and geometry are retained. This guards against a green stored witness with an empty transcript; inspect the actual text in retained screenshots too. Event filters explicitly distinguish canonical turn events from message-state records without removing the exact turn-count checks.

Evidence includes real desktop screenshots before sending, after both replies and after restart, painted bubble counts, action traces, synthetic room/canonical witnesses, binary identity and cleanup checks under `verify-rooms`. The hosted Windows/Linux boundary contract test also verifies legacy refusal, broadcast fan-out, command replay and read-after-reopen idempotency. It is not desktop proof by itself.

## Gotchas

SSH, host ownership and provider stdin/output are explicit stand-ins. Production canonical message transactions and host event reducers execute in-process on Windows; there is no real remote host subprocess or paid provider call. The fixture extracts the embedded production SQLite schema and runs its actual RoomStore/RoomBridge handlers. POSIX store ownership and dispatch locks are not verified on Windows. No private-chat fallback is allowed.

This preview journey does not establish release readiness, real-provider delivery, mention targeting, uncertain delivery retry, cross-room isolation, scoped restart, Android compatibility, themes or independent design QA. Those remain separate acceptance gates. Inspect exact-source `build.json`, `result.json`, witnesses and screenshots before claiming any passed outcome. A green preview must not enable release or merge the parent Rooms implementation by itself.

No raw profile, account record, credentials, app logs or memory dumps enter public artifacts. All visible messages and identities are synthetic and must be labelled that way wherever screenshots are attached.
