# Browser session switch speed

## Sub-features

- Real Ctrl+Tab latency in console view and Chat View, each with browser panes off, warm, and freshly frozen.
- Browser-on completion requires the target session's solid-color page to be painted on screen, not just a visible Chrome HWND.
- IGSH-724 setup checks Alt+Q from the native address bar back to console or composer and then into the page: Space, Down, j and k must each update the synthetic page's key counter in its title. F6 must still reach the address bar; reopening the existing pane through the palette must send Space into the page again. Both console and Chat View retain exact input identity and unsent drafts.
- IGSH-972 repeats the Alt+Q round trip five times per session after that first check and requires every Space, Down, j and k to reach the page counter, so a lone Alt release that opens the browser menu fails the run. The handoff injects its Alt unlock and mask key on one timer tick while the session window still has focus and switches the foreground on the next tick, so no Alt event reaches the browser.
- Separate window-visible, wake-flag-cleared and painted timings distinguish docking from compositor latency.
- Every sample must be a real switch: before input the other session must be the visible foreground one and the target must not be ready, and afterwards the app log must hold exactly one `switch-timing:` line to the target (plus the freeze, Ctrl+Tab and wake lines for frozen samples), or the journey fails.
- The named `switch-gap` case fails if either view's warm or frozen browser-on median minus browser-off median exceeds 50 ms, or any required end state cannot be reached.

## How to get to it (user POV)

- Start with a CMD in console view. Move it to a new group through Ctrl+K `move to group`, Enter, `new group`, Enter, Esc. Create an ungrouped second CMD with Ctrl+K `new cmd`, Enter. The group precedes Recents, keeping Ctrl+1/Ctrl+2 aligned with saved tabs 0/1; Ctrl+Tab cycles between them.
- Open each session's browser with Ctrl+K `open browser`, Enter. Ctrl+K `jump browser`, Enter focuses its native Chrome window. Ctrl+L, type a synthetic `data:text/html,` URL, Enter loads that session's full-viewport color. The journey installs the repository bridge extension and a test-only native host in the disposable runner profile; no account, private messages or injected session state is needed.
- Use Chat View off everywhere through the real palette to establish both shell baselines, then use Alt+C in both sessions. Distinct unsent synthetic composer drafts identify the target session without sending a message.

Chat View: the two drafts start with different characters (`W` and `.`), setup captures the first-character cell of each session's composer once the paint is stable, picks the 3x3 patch where the two sessions differ most, and polls until that patch matches the target session's reference.
6. Browser-on additionally requires the distinct target browser HWND visible with the correct ownership and exact previously observed dock rectangle. Record that end-state time as `window_visible_ms`. A plain GDI BitBlt (SRCCOPY, no CAPTUREBLT) samples a 3x3 patch halfway across and three-quarters down the dock, below the native toolbar. All nine pixels must match the target's color within eight levels per RGB channel. Stop only when both the surface/window state and the target color hold. Before every sample of every set, the source session's color must be on screen and the target's absent, and before each set the first session's color must be on screen, so an already-wrong starting state cannot produce a false sample. 7. Save `switch-timings.json` unconditionally from finally. Each of the six named sets contains `samples_ms`, `median_ms`, `window_visible_ms` and `window_visible_median_ms`. A sample whose log range does not hold exactly one `switch-timing:` line to its target fails the journey, and a frozen sample also needs its freeze confirmation, the Ctrl+Tab hook line and the wake line for the target shell in order. 8. Record per-view browser HWNDs, dock rectangles and target colors in `browser_on-window-identities.json` and `chat_browser_on-window-identities.json`. Preserve before, per-mode action and after screenshots, UIA/focus evidence and raw logs. The case records the setup/sample phase on any failure; no synthetic successful sample substitutes for a missing state.

The complete raw debug log is also retained under `evidence/data`. This journey gets a 60-minute job budget, including up to ten 150-second freeze waits; other journeys keep 30 minutes.

## Gotchas

- The fixture disables tier-three idle window closing, not tier-two freezing. Ctrl+Tab deliberately preserves Recents ordering and does not refresh `last_viewed`; otherwise the fifteen-minute close policy can remove a pane during the fresh-freeze sets. Every frozen sample must still observe a fresh app-published marker and painted return.
- CMD sessions now publish the same shell-ID freeze marker as remote sessions. Older executables without that marker or a usable extension/CDP binding fail the frozen precondition and retain null samples; they are not silently measured warm. The marker is published only after a successful `Page.setWebLifecycleState frozen` acknowledgment and cleared only after a successful wake acknowledgment.
- The extension uses a fixture public key for a stable derived ID and a runner-only Chrome native-host registration. The app uses pinned Puppeteer Chrome for Testing through its normal `chrome-exe.txt` and `browser-engine.txt` configuration; the journey waits up to 90 seconds for the extension keepalive to reconnect the native host. Existing registration is never overwritten; cleanup removes only the key created by this journey and the copied fixture files with the scratch profile.
- CDP `active` can leave a previously frozen page hidden. The lifecycle debugger session retains focus emulation while awake and disables it before freezing; this affects page visibility, never Windows foreground or keyboard focus. Tab close and debugger detach release the session; reset rebuilds only an already-awake visibility lease.
- The journey itself is measurement, not a switch-speed fix. Static tests do not prove Windows parsing, execution, painting or latency; those checks belong to CI.
- Browser visibility settle retries every 100 ms; console geometry settle runs after 180 ms. These are retry cadences, not intentional waits before the initial show.
- SWP_ASYNCWINDOWPOS and ShowWindowAsync trace dispatch, not browser-process composition. The screen-color check includes visible completion, while window-visible timing remains available separately.
- Unsent Chat View drafts are synthetic target markers, never messages. The transcript need not contain a signed-in agent conversation.
- Debug logging can add overhead in both modes. The native loop removes the PowerShell transition and any UIA/disk work after starting Stopwatch; actual floor reduction must be measured in CI rather than inferred from source.
- Only the app-owned native browser is navigated. The check rejects lost ownership/focus, parked HWNDs, missing state and blank or wrong-session pixels; the normal user browser is never touched.
- IGSH-998: after Palette "open browser" and Enter, the journey waits for the app log line `pane_hop result bh_fg=true`, read from an offset taken before Enter, and only then runs the unchanged strict foreground and Space checks. The hop is timer driven and finishes 290 to 384 ms after Enter, while Chord sleeps a fixed 250 ms, so the old instant check raced the app.
- IGSH-1006: the 50 ms gap used to compare browser-on, whose completion included one screen capture (47 ms over a Chrome window with CopyFromScreen, 32 ms with BitBlt, 16 to 29 ms over a console), against browser-off, which read no pixel. App switch work was 17.5 ms both ways and the window-visible gap was only 13 to 31 ms. Both sides now finish on the same kind of read, so `samples_ms` for browser-off is higher than before; `window_visible_ms` keeps its old meaning on both sides for continuity. The gate is still 50 ms.
